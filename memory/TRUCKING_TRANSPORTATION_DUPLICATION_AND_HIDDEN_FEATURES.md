## A · Duplications & overlaps

### A1 · Top cleanup signal surface mirror (3 surfaces, 1 engine)

The same `signals[0]` from `build_cleanup_signals()` is rendered
in three places:

1. **Cleanup Companion tab** (`/admin/transportation/intelligence/cleanup`)
   — admin-only; the full 12-signal list + materializer (Track 16.15).
2. **Transportation Dashboard top cleanup card** —
   `TopCleanupOpportunityCard` in `_views.jsx`; admin-only
   dashboard mirror (Track 16.15A).
3. **Operations Center health widget · Action Items tile** —
   cross-portal read; consumes the materialized
   `transport_action_items` count, not the raw signal scan
   (Track 16.16).

**Verdict:** intentional, tolerable. No duplicate scoring; all
three surfaces read the same engine output.

### A2 · Eligibility chip mirror (4 surfaces, 1 collection)

The eligibility state of a carrier / driver / truck appears on:

1. The entity's admin workspace (`/admin/transportation/persons/{pid}/workspace` etc.).
2. The dispatch board (via `/api/dispatch/transportation/eligible-*`).
3. The dispatch readiness summary (Track 16.06 dispatch mirror).
4. The Track 16.16 readiness card (PM / Operations widget).

**Verdict:** intentional. `transport_eligibility_state` is the
single source; gate (Track 16.09) is the single writer.

### A3 · HR ↔ Transportation health surface (2 surfaces, 1 engine)

`scan_hr_transport_consistency` output is rendered on:

1. Admin Transportation Dashboard HR Sync widget (Track 16.11A).
2. Track 16.16 readiness card → risk banner when mismatches > 0.

**Verdict:** intentional. Same engine, two audiences (Admin sees
detail; PM/Operations see only the count + risk banner).

### A4 · Equipment Dashboard re-mount (3 portals, 1 component)

`EquipmentDashboard` is mounted at:

1. `/admin/equipment-inspections` (Admin)
2. `/pm/equipment` (PM)
3. `/shop/equipment` (Shop)

Same component, role-scoped data. **Verdict:** intentional, by
design — mirrors the Track 16.07 workspace philosophy.

### A5 · Fleet visibility re-mount (4 portals, 1 component)

`FleetVisibility` is mounted at:

1. `/pm/fleet`
2. `/shop/fleet`
3. `/safety-portal/fleet`
4. `/dispatch-portal/fleet`

`scope` prop drives the data filter. **Verdict:** intentional.

## B · Hidden / unreachable features

### B1 · None found at the route or endpoint level

Every backend endpoint maps to a UI surface or a documented
public token flow. Every frontend route is reachable from at
least one navigation surface.

### B2 · Internal nav-only surfaces (technically reachable, but deep)

`AdminTransportation` (`/admin/transportation/*`) is a single
route in `App.js` that mounts a nested SPA
(`pages/transportation/TransportationApp.jsx`). The following
sub-surfaces are reachable ONLY via internal nav (`tx-intel-tab-*`
data-testids):

- Compliance Dashboard
- Carriers list
- Drivers list
- Trucks list
- Document review queue
- Inspection queue
- Audit timeline
- Orientation Center
- Automation Center
- Command Queue
- Intelligence Center
  - Executive dashboard
  - Operational health
  - Recommendations
  - Predictions
  - Dispatch learning
  - **Cleanup Companion** (Track 16.15)
  - **Top cleanup signal mirror** (Track 16.15A on the dashboard
    tab)

**Verdict:** by design. No fix needed. Worth documenting deep
links in the unified Command Center architecture (Track 17.01).

## D · Schema / collection observations

### D1 · `transport_employees` has no admin UI of its own

This collection is owned by Track 16.11 HR Lifecycle Integration.
It is a derived HR-driven mirror that drives eligibility
recompute when HR lifecycle events fire. It surfaces through:

* `transportation_dashboard_hr_health()` (Track 16.11A) → HR
  health widget on Admin Transportation Dashboard
* `transportation_status` per-employee → HR Driver Qualification
  Dashboard

**Verdict:** documented, no UI gap.

### D2 · Duplicate audit collections

Three audit collections exist for the transportation domain:

1. `audit_events` — unified platform timeline (cross-domain).
2. `transport_intelligence_audit` — Track 16.12 / 16.13 reads
   + recommendation surface lineage.
3. `transport_dispatch_recommendation_audit` — Track 16.13 / 16.14
   interaction audit + learning loop.
4. `email_routing_audit_v2` — Track 16.05 email routing.

**Verdict:** each has a distinct purpose. No duplication.

### D3 · Two dispatch state-machine sources

- `dispatch_state_events` (per-transition history)
- `dispatch_continuity_events` (breakdown / recovery extensions)

They cover non-overlapping event spaces. **Verdict:** intentional.
