# MASCI Operational Execution Constitution

## 1. Constitutional Authority

This document is the supreme governing authority for the MASCI OPS Operational Execution build.

It governs the Operational Work Foundation, Rolling Two-Week Scheduling, Daily Execution, Daily Report integration, Operational Data Spine projections, Weekly Reconciliation, Daily Company Operations Briefing, Trust Spine participation, search projection, certification, and release governance.

No implementation track may contradict this constitution.
No implementation track may invent a competing owner, competing identifier, competing lifecycle, competing publication rule, competing dashboard authority, competing briefing authority, competing scheduling authority, competing reconciliation authority, competing Trust Spine requirement, competing certification rule, competing ODS projection rule, competing AI authority, competing search authority, competing audit chain, competing security model, competing API contract, competing schema, competing migration path, competing release rule, or competing performance rule for any governed concept.

Where MASCI already contains a canonical source or proven domain authority, implementation must extend that authority rather than replace it.

This constitution is binding on:
- backend implementation
- frontend implementation
- data modeling
- API design
- search
- ODS projections
- Trust Spine events
- AI outputs
- dashboards
- executive briefings
- PDFs and exports
- notifications
- certification
- release sequencing
- production deployment

Implementation is constitutionally blocked until these governing artifacts are accepted.

## 3. Permanent Platform Philosophy

### 3.1 Field First
The field operator is the primary creator of execution evidence. Architecture must reduce burden, preserve field-entered facts, and minimize ambiguity under real jobsite conditions.

### 3.2 Operations First
MASCI OPS exists to run construction operations. New features must improve execution, coordination, planning quality, recovery, reconciliation, decision quality, or operational trust.

### 3.3 Mobile First
Every field workflow must be operable on phone and tablet first. Desktop may enhance; desktop may not be a prerequisite for core field execution.

### 3.4 Trust First
Every surfaced value must be explainable. Every derived value must declare its source, freshness, and confidence. AI output must never masquerade as verified operational fact.

### 3.5 Production First
No architecture is complete until it is deployable, observable, certifiable, recoverable, and supportable in production.

### 3.6 Continuity First
Operational truth must survive device lock, network interruption, tab close, session change, duplicate submission attempts, partial save, delayed synchronization, and replay.

### 3.7 Survivability First
Failure must degrade safely. No silent data loss. No silent drift. No irreversible mutation without evidence, authority, and audit.

### 3.8 One Platform
Scheduling, Daily Reports, Dispatch, Shop, Equipment, Fleet, Safety, HR, QA/QC, Trust, Search, ODS, and Executive Briefing are projections of one operational reality.

### 3.9 One Ecosystem
No portal-specific business truth, no dashboard-specific KPI formula, no duplicate briefing engine, no duplicate notification engine, no duplicate intelligence engine, and no duplicate status engine may be introduced.

## 4. The Eight Mandatory Engineering Pillars

Every implementation must be:

1. **Powerful** — capable of supporting real enterprise heavy-civil operations
2. **Simple** — understandable and usable under field pressure
3. **Beautiful** — consistent with MASCI visual and interaction language
4. **Trusted** — explainable, auditable, and truth-preserving
5. **Proven** — grounded in evidence, not assumption
6. **Deployable** — buildable, releasable, observable, supportable
7. **Durable** — resistant to drift, shortcut architecture, and disposable logic
8. **Relentless Ownership** — every discovered defect is repaired or formally owned

Failure to satisfy any pillar means implementation is incomplete.

## 5. Permanent Engineering Mandate

### 5.1 Relentless Ownership Rule
Every implementation track must inspect every touched file, workflow, API, component, schema, route, projection, dashboard, report, AI workflow, notification, Trust Spine event, ODS projection, search projection, and user experience affected by the change.

If a defect, inconsistency, architectural weakness, technical debt, duplicated logic, incorrect ownership, misleading behavior, broken workflow, poor UX, performance issue, security concern, stale code path, dead code path, incomplete implementation, certification gap, documentation gap, or constitutional conflict is discovered, it must be evaluated immediately.

If it can be safely repaired inside the approved scope without architectural drift, it must be repaired in the current track.

If immediate repair would create unacceptable architectural risk, require new constitutional decisions, or materially widen scope, it must be formally recorded with:
- precise description
- root cause
- impact
- recommended resolution
- dependency analysis
- owner
- implementation priority
- certification impact

No known defect may be silently ignored.
No engineer or AI agent may knowingly leave the platform in a worse state than it was found.

### 5.2 Continuous Quality Rule
Every touched area must be left better than it was found:
- more consistent
- more understandable
- more maintainable
- more reliable
- more testable
- more performant
- more secure
- more beautiful
- more trustworthy

### 5.3 Zero Drift Rule
Repairing defects does not authorize architectural drift.

Do not invent new systems.
Do not duplicate existing systems.
Do not fork canonical ownership.
Do not redesign unrelated modules.
Improve the existing architecture.
Do not fork it.

### 5.4 Stop Rule
Never stop because the originally requested feature appears to work.

Stop only when:
- the requested implementation is complete
- all affected areas satisfy the Eight Pillars
- all discovered in-scope defects are repaired or formally classified
- regression protection has been added
- certification evidence has been updated
- the implementation is release-ready for its authorized scope

"Feature complete" is not "implementation complete."

## 7. Core Domain Authorities

### 7.1 Job / Project
The job/project is the canonical operational container.

- canonical owner: `jobs_master`
- canonical identifier: `project_number`
- primary human label: `project_name`
- canonical staffing ownership: `project_team_assignments`

Jobs/projects may be referenced by schedule, Daily Reports, Dispatch, briefing, and reconciliation, but may not be redefined in those systems.

### 7.0 Organization / Tenant
The organization/tenant is the canonical top-level security and ownership boundary.

- canonical owner: organization / tenant authority
- canonical identifier: `tenant_id`
- normative catalog: `MASCI_OPERATIONAL_EXECUTION_CONSTITUTIONAL_APPENDIX.md` §2 and §8

### 7.01 Person / Professional Identity
Person/professional identity is distinct from employee/company membership, email address, portal account, or display label.

### 7.02 Employee / Company Membership
Employee/company membership is the canonical governed relationship between a person and the company within a tenant.

### 7.03 Daily Company Operations Brief Source Rule
The Daily Company Operations Brief is the canonical executive publication layer only. It is never source truth.

### 7.2 Operational Work
Operational Work is the canonical planned and owned unit of field execution.

It is not a Daily Report.
It is not a Dispatch assignment.
It is not a PM work order.
It is not an HR record.

It is the canonical scheduleable, reconcilable, traceable unit of execution tied to project, work area, cost code, owner, and time context.

### 7.3 Rolling Two-Week Schedule
The Rolling Two-Week Schedule is the canonical near-term commitment layer.

It is a projection over Operational Work, not an independent truth source for work identity.
It may sequence, group, commit, block, and carry forward Operational Work.
It may not redefine the work object.

### 7.4 Daily Execution
Daily Execution is the factual record of what happened on a given operating day.

Its primary field evidence source is the Daily Report workflow.
Other domains may contribute supporting evidence, but they may not silently overwrite Daily Report source facts.

### 7.5 Daily Report
The Daily Report is the canonical operator-entered daily execution record for a project, date, and report instance.

It is authoritative for facts entered on that report, including:
- crew participation
- crew time
- equipment usage
- production entries
- materials and outbound materials entered there
- delays and constraints entered there
- weather and field narrative entered there
- photos and evidence attached there

It is not the planner of future work, but it is a canonical actuals source for reconciliation and briefing.

### 7.6 Weekly Reconciliation
Weekly Reconciliation is the canonical process for comparing planned work, committed work, and actual work.

It must classify and preserve:
- planned
- committed
- actual
- partial
- blocked
- cancelled
- unplanned
- carry forward
- variance
- root cause
- lessons learned
- recovery actions

### 7.7 Daily Company Operations Brief
The Daily Company Operations Brief is the canonical executive operational publication for the prior operating period.

It is derived.
It is never a primary source of fact.

It must separate:
- verified facts
- calculated metrics
- AI-assisted narrative
- unresolved or low-confidence signals

### 7.8 Trust Spine
The Trust Spine is the canonical cross-workflow lifecycle evidence layer.

It is not a replacement source record.
It proves what operational workflow stages did or did not occur.

### 7.9 Operational Data Spine
The Operational Data Spine is the canonical cross-domain read fabric for operational aggregation.

It is a projection and aggregation layer.
It is not an alternate write authority.

## 11. Canonical API Governance

### 11.1 API Contract Audit Requirement
Every governed endpoint must declare:
- route and method

- canonical owner

### 11.2 Locked Contract Rule
Frontend and backend must be kept contract-locked.
No implementation may silently change field names, response envelopes, status meanings, filtering semantics, pagination semantics, sort semantics, or error shapes without explicit contract update and certification.

### 11.3 Idempotency Rule
Every mutation endpoint must explicitly declare duplicate-submit behavior.
It must define whether the operation is:
- naturally idempotent
- protected by idempotency key
- protected by source-record uniqueness
- intentionally non-idempotent with justification

### 11.4 Validation and Error Rule
Validation errors, authorization errors, conflict errors, not-found errors, stale-version errors, and dependency-blocked errors must be distinguishable.
The API may not collapse materially different failures into misleading generic success or ambiguous failure.

### 11.5 Consumer Lock Rule
Every endpoint must identify its downstream consumers, including:
- field UI
- management UI
- dashboards
- search
- ODS
- exports
- background jobs
- notifications
- AI workflows

No endpoint may be treated as isolated if consumers exist.

### 11.6 Manual Save and Deployment Boundary Rule
No implementation prompt, API contract, or workflow description may imply that Emergent saves to GitHub or deploys preview/production.

### 17.2 Graceful Recovery Rule

- preserving user-entered facts

- surfacing truthful status

### 17.3 No Silent Failure Rule

- what audit or telemetry is required
- what the operator sees during degraded state

Local continuity artifacts may assist operators.
They may not become hidden alternate enterprise truth.

Historical Daily Reports, schedule publications, reconciliation verdicts, and executive briefs may not be silently reinterpreted by later logic without preserving the original version context.

### 24.3 Deletion Rule
Evidence-bearing operational history may not be hard-deleted in normal operations.
Archival, withdrawal, supersession, or governed soft-retirement must preserve traceability.
