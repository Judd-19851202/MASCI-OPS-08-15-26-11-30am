# WP16 Operator Trust Guidelines

## Objective
Trust is part of the interface. Operators should feel oriented, informed, and safe to proceed.

## Evidence-first UX
- Important confirmations must explain what changed.
- Important confirmations must explain when it changed.
- Important confirmations must explain who initiated the change when available.
- Important confirmations must reference evidence or system traceability where appropriate.

## Error standard
Every important error must answer:
1. What happened?
2. Why did it happen?
3. What should I do next?

## Coaching standard
- Coach without lecturing.
- Keep instructions short and action-oriented.
- Prefer direct verbs: Review, Submit, Assign, Repair, Confirm.
- Avoid internal engineering vocabulary unless the audience is explicitly technical.

## Navigation trust
- Operators must never feel trapped in a screen.
- Cancel and close actions must be distinct from save actions.
- Back paths must preserve context whenever possible.
- Search and command access must stay available at the shell level.

## Content trust
- Use one canonical name per concept.
- Avoid contradictory status labels.
- Avoid generic placeholders that hide meaning.
- Use timestamps in operator-local time where presented.
